# R4 — 1.0 Reliability / Coverage Gate

Base: `origin/main` `a4a2f4f95b339644b1541d9312ecb517a8b047cf` (verified). Version unchanged (not 1.0.0). No Market
Intelligence, no Upgrade Finder, nothing from the ENGINE/ASTRA branch.

## 0. What this pass could and could not do

This pass ran in a Linux cloud container with **no PoB2 runtime** (PoB2's headless engine needs the Windows
`lua51.dll`; the PoB2 source archive was not reachable). So:

- **Not executed:** every real-PoB / `build_corpus` test, the corpus report's engine results, any performance
  measurement, any new fixture.
- **Executed:** all engine-free suites (policy units, the corpus-report tests, the new gate tests, the 5 engine-free
  suites the report generator runs).
- **Method:** static audit of tests, registry, Lua bridge and Python source; engine results are only the last recorded
  ones, labelled as such.

Everything below that needs a PoB2 machine is listed in §12 as a pre-merge / pre-1.0 condition rather than claimed.

## 4. `stat_stacker`

**Verdict: B — redundant; the taxonomy was wrong, not the corpus.** The category appears only in the original M1.1
list; nothing defines it. The mechanic it names — damage or defence driven by an accumulated stat — is already
represented by real builds: Strength (Brutus' Lead Sprinkler), Dexterity/Intelligence (Hand of Wisdom and Action) and
maximum Mana (Rathpith Globe, "damage and crit per 100 maximum Mana", Eldritch Battery). These are `attribute_stacker`
(13 cases) and `mana_scaling` (7). `stat_stacker` is now a **derived umbrella** (`DERIVED_ARCHETYPES`): covered iff a
constituent is, listed through them, never given invented cases. A genuinely uncovered sub-population remains and is
stated, not hidden: **charge / Rage / Armour-or-Evasion-to-damage stackers have no real fixture.** PoB takes charges and
Rage as configured counts, which the policy already treats as UNCERTAIN (`POISON-CONFIGURED-STACKS-UNCERTAIN`), so this
is a documented limitation, not a release gap; no fixture was added because none could be verified without an engine.

## 6. Jewel audit (existing Item Intelligence baseline; no new system)

Static; real-PoB evidence is the existing `test_jewel_real_pob.py` / `test_jewel_restore_remediation.py`. Those suites
were **not** in the coverage report at all; 7 jewel cases are now registered (never yet reported).

| Question | Answer |
| --- | --- |
| Single replacement? | Established (real PoB): occupied socket replacement, FULL, restore passes. Only one candidate type has ever been tested (a plain rare Ruby). |
| Several allocated sockets? | Established on two builds (5 and 4 sockets): one batched transaction, each baseline is its own equipped jewel, distinct verdicts, a TRADEOFF row. |
| Deterministic target selection? | Discovery is ascending node id; ranking ties break on the slot *string* (`"Jewel 11184"` before `"Jewel 2491"`): deterministic, not numeric, and not told to the user. No user setting selects a socket. |
| Occupied replacement / restore safe? | Yes by design and test: transaction snapshots equipment, allocation, overrides, masteries; fingerprint (incl. jewels, tree nodes) verified; any failure fails closed with nothing delivered. No test drives the corrupt-restore fault on a jewel. |
| Empty **allocated** socket? | **Not established.** The test is skipped (no fixture has one) and is deliberately not registered. By code path an empty allocated socket *is* offered and evaluated as "replacing empty jewel socket" (UI copy unit-tested on synthetic dicts only). Residual risk: the restore fingerprint hashes `spec.jewels`; if PoB writes `0` where the baseline had `nil` it would fail closed as "restore failed". Fail-closed, so not a wrong-answer risk. |
| Several-jewel build truthful? | Yes, with one disclosed-to-nobody exclusion (below). |
| UI ambiguity? | Compact tooltip shows only "Best fit: Replacing <name> · Checked N jewel sockets"; two same-named jewels are indistinguishable. The drawer's "Socket 1…N" is the *ranked* position for that candidate, not a stable identity. Raw `Replace Jewel 11184` can surface on some surfaces (unverified which). |

Gaps found: (a) **fixed here** — when every allocated socket held a connectivity-risky jewel the user was told the jewel
was "not compatible with any allocated jewel socket"; false (nothing was tried). It now says the sockets could not be
compared safely (`no_compatible_jewel_slot_error`, 4 unit tests). (b) Excluded sockets (Split Personality-style jewels)
are counted in diagnostics and never shown to the user: "Checked N" silently omits them. (c) A doc/code tension: the
coverage matrix lists "From Nothing"-like jewels as covered while the bridge excludes jewels flagged `intuitiveLeapLike`;
which sockets are repaired versus excluded is asserted nowhere. (d) Candidate Timeless / radius / "Allocates" jewels go
straight to PoB with no refusal and no test.

**Blocker judgement:** the empty allocated socket is arguably the main "should I slot this?" case, but the product path is
correct by inspection and fails closed. It is a **1.0 condition to verify, not a known defect**: prove it with one
synthetic build with an allocated, empty socket (also exercises the `spec.jewels` question) on a PoB2 machine. Do not
convert the skip into coverage until then.

## 10. Build Intelligence audit (separate from Item Check)

The analysis features live in `src/exilelens/analysis/` (not `items/build_intel/`, which is item-side).

- **Evidence is mostly docs, not tests.** Only 2 real-PoB tests (fingerprint, sensitivity) on 2 builds, neither asserting
  restore, priorities, Fix First or strongest responses. The rest is FakeEngine unit tests plus one-off validation
  scripts recorded in docs (18-build M5.4/M5.5, 12-build R1, 11-build R1.5) whose artifacts are gitignored — the numbers
  cannot be re-checked from the repo.
- **Restore/cache:** `run_probe` fails a probe on `restore.pass == false`, but there is **no unit test of that branch** and
  the fake engine always returns `pass=True`; the computed `fingerprint.match` is recorded, not enforced. The probe cache
  key (`fingerprint|generation|probe|magnitude|context`) is cleared on reload/invalidate and tested with a constant
  fingerprint only — no test changes the fingerprint without invalidating.
- **Not-comparable rule: respected, with a P2 note.** No per-point value is exposed (tests forbid `per_unit`/`per_point`/
  summed percentages). Strongest tiles carry an explicit caveat; ladder and lane rows always show the tested amount next
  to its response and the window states each stat was tested once at that amount. The ladder *ordering* has no
  separate caveat. Item Check's "your strongest measured damage response" line does not mention the increment. SearchIntent
  / Build Value rank profile-weighted values and are outside the per-point guard tests (hidden by default).
- Known limits unchanged and P2: regeneration responses not captured, life-paid costs not interpreted, weapon slots not
  analysed per slot, curves have two points, chaos resistance leads Fix First on 10 of 18 corpus builds.
- No normalization introduced.

Gate consequence: a Build Intelligence output *confidently stating something not established* was not found; the
missing evidence is test coverage of restore/cache failure paths (§12).

## 11. The 1.0 reliability gate

Machine-checkable part: `tests/corpus_coverage/gate.py`, `python scripts/generate_corpus_coverage_report.py --check-gate`
(exit 0 PASS/CONDITIONAL, 1 FAIL, 2 INCONCLUSIVE). The only numeric threshold (`MIN_FULLY_MEASURED = 70`) is the measured
count when the gate was defined, so coverage can grow but not shrink.

**BLOCK 1.0:**

| Criterion | Protects |
| --- | --- |
| `NO_WRONG_RESULT` | Any reproducible WRONG_RESULT / WRONG_UNCERTAIN in the corpus. |
| `STATE_INTEGRITY_ALL_PASS` | Restore/cache corruption; wrong loadout/weapon-set/socket evaluated silently; nondeterminism (35 cases). |
| `EVERY_VERDICT_CASE_CLASSIFIED` | A supposedly supported path with no declared evidence. |
| `NO_UNREPRESENTED_ARCHETYPE` | A major archetype with no case. |
| `MAJOR_ARCHETYPES_FUNCTIONALLY_MEASURED` | 14 major archetypes each need a passing FULLY_MEASURED case (a refusal does not count). |
| `FUNCTIONAL_COVERAGE_RATCHET` | Silent shrinkage. |
| `RESULTS_ARE_CURRENT`, `ALL_CASES_EXECUTED` | The gate cannot pass on carried-forward or missing results. |

**ALLOWED with documented limitation (CONDITIONAL):** `NO_NOT_ESTABLISHED` failing (named, listed gaps); intentional
UNCERTAIN/UNSUPPORTED/PARTIAL (explained per case); mechanics PoB cannot establish; niche mechanics with a safe fallback.

**Not machine-checkable — manual 1.0 conditions:** M1 gate executed (not carried) on the release-candidate commit and
PASS/CONDITIONAL; M2 empty-allocated-jewel-socket proven or accepted in writing; M3 performance baseline recorded; M4
the five NOT_ESTABLISHED assertions added and run; M5 Buckler/offhand-type check on an engine; M6 Build Intelligence
restore/cache failure-path unit tests (engine-free).

Current machine result on the committed report: **INCONCLUSIVE** — structure passes (no unclassified, no unrepresented
archetype, 70 ≥ floor, no wrong results among the carried data); results are carried or missing; `life_scaling` has no
current passing FULLY_MEASURED case (LIFE01 never reported).

## 12. Remaining release blockers / conditions

No known reproducible WRONG_RESULT, state corruption or confidently-wrong output was found. What stands between this
and a PASS:

1. **Run the report on a PoB2 machine against the release candidate** (replaces carried data; also first-ever results for
   LIFE01, RECOVERY02A and 7 jewel cases). Expected: no WRONG_*; if any appears it is a finding of this gate.
2. **Performance baseline (not captured).** Use `scripts/r1_product_validation.py`, which already records Item Check warm
   median, Analyze Build cold seconds/recalcs and repeat seconds/recalcs/cache per build, plus the worker-call counter.
   Docs hold only ad-hoc, unnamed-machine figures (warm Item Check ≈0.7–2.0 s; Analyze Build 40–68 s cold, 6–8 s repeat;
   a transaction ≈ 3 recalc frames × ~250 ms; jewel batch N+2 frames). Instrumentation gap: `TooltipPerfTrace` is never
   instantiated, so there is no hotkey-to-paint number. R5/R6 need a recorded baseline before they start.
3. Empty allocated jewel socket (§6). 4. Add to `RING-EMPTY-SLOT`, `BOW-QUIVER-REPLACEMENT` `evaluation_quality == "FULL"`
   (+ direction), to the two jewel cases and `RECOVERY02A` their quality/verdict assertions; then reclassify. 5. Buckler /
   one-hand collateral-offhand disclosure / weapon-set naming (P2 copy, engine tests needed). 6. Build Intelligence
   `run_probe` restore-failure and fingerprint-change cache tests.
